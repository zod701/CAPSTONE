# API 예산을 갖는 순차 검증 파레토 탐색

`lazy_pareto.py`는 시간·요금이 아직 확정되지 않은 **유한한 경로 후보 집합**을 검증하는 연구용 탐색기다.
앞서 구현한 `pareto_search.py`는 고정 비용 그래프에서 택시 0/1회 경로를 정확히 찾는다.
이번 모듈은 그와 별도로, API를 모두 호출할 수 없을 때 어느 후보의 비용을 먼저 확인할지 다룬다.
택시 1회 제약과 환승 이력은 입력 후보의 생성·평가 단계가 보존해야 한다.
데모 웹의 하이브리드 탐색([web/backend/app/hybrid.py](../web/backend/app/hybrid.py))이 이 탐색기로 확인할 후보를 고른다(예산 30 · `parallel=3`).

## 입력과 상태

후보는 `Candidate(id, estimate, queries, lower_bound)`다.

- `estimate`: 검증 순서에만 쓰는 추정 총시간·총요금.
- `queries`: 그 후보의 실제 비용을 계산하는 데 필요한 고유 질의 목록. 출발·도착 방향을 포함한다.
- `lower_bound`: 모든 유효한 검증 결과보다 시간·요금 각각 작거나 같다고 **입력자가 보장한 값**.
  근거가 없으면 `(0, 0)`을 사용한다. 택시 ETA 근사값이나 경험적 오차 구간은 인증 하한이 아니다.

핵심 탐색기는 A/B/C/D, 후보 출처, 지역을 받지 않는다. 요청 시간가치와 경로 전체의 비용만 사용한다.
검증한 경로, 실제 지불한 질의 응답, 실패한 질의, 진행 중인 질의 묶음, 미검증 후보를 유지한다.

`fetch(query)`는 비동기 조회 함수다. `evaluate(candidate, responses)`는 후보에 필요한 **지불 완료 응답만** 받아
`Cost(time_s, fare)`를 반환한다. 알려진 경로 없음·정책 미달은 `None`, 결과 미상은 `QueryUnavailable`로 구분한다.
평가기 안에서 외부 데이터를 더 조회해서는 안 된다. 구현 오류는 실패로 숨기지 않고 호출자에게 전파한다.

## 선택과 제거 조건

첫 검증은 요청 시간가치 `v`에서 추정 점수가 가장 낮은 후보로 시작한다.
이후에는 실제 검증 결과의 파레토 집합 `F`를 기준으로 다음 후보를 고른다.

\[
S_v(t,f)=f+v\,t/60
\]

후보 `c`의 아직 지불하지 않은 질의 수를 `m(c)`라고 하면:

\[
\Delta(c)=\max(0,\min_{p\in F}S_v(p)-S_v(\hat c))
\]

\[
G(c)=\max\left(0,\min_{p\in F}\max\left(v\frac{t_p-\hat t_c}{60},\ f_p-\hat f_c\right)\right)
\]

`Δ`는 추천 점수의 예상 개선액이다. `G`는 현재 검증 결과가 아직 덮지 못하는 절충안의 공백을 원 단위로 표현한다.
검증된 경로가 추정 후보를 지배하면 `G=0`, 더 빠르거나 더 싼 새 절충안을 제시하면 양수가 된다.

다음 순서로 비교한다.

1. `Δ>0`인 후보가 있으면 `Δ/m`이 큰 후보.
2. 동률이거나 추천 개선 후보가 없으면 `G/m`이 큰 후보.
3. 여전히 같으면 추정 점수가 낮은 후보, 마지막에는 고정된 ID 순서.

이는 예산 내 질의 순서를 정하는 휴리스틱이다. 추천 개선 추정이 계속 낙관적이면 다른 절충안 탐색이 밀릴 수 있다.
기존 자료의 시간 오차 방향이 OD마다 달랐으므로 전역 보정 상수나 유형별 우대 규칙은 넣지 않았다.

**추정 비용이 지배됐다는 이유로 후보를 영구 제거하지 않는다.** 영구 제거는 검증된 경로 `p`가
후보의 인증 하한 `LB(c)`를 두 축에서 모두 지배할 때만 한다.

\[
(t_p\le LB_t(c))\land(f_p\le LB_f(c))
\]

같은 비용쌍의 다른 경로까지 모두 반환하는 것이 목표는 아니므로 약한 지배도 제거에 사용한다.

## 예산과 보장

`await search.advance(5)` 이후 `advance(10)`은 5회를 더 쓸 수 있다는 뜻이다. 인자는 **누적 질의 상한**이다.
두 질의가 필요한 후보에서 하나만 조회하고 멈춰도 그 상태를 이어간다. 잔여 예산에 맞추려고 다른 후보로 교체하지 않는다.
공유 응답으로 완성된 다른 후보도 모두 평가하며, 실패한 조회는 과금하고 반복 호출하지 않는다.

`advance(n, parallel=k)` 는 한 번에 최대 `k` 개 질의를 함께 보낸다. 첫 질의는 위 규칙의 1순위 후보 것이고, 나머지는 같은 시점의
다음 순위 후보들의 아직 안 낸 질의다 — 서로의 응답을 보지 않고 고르므로 `k = 1` 의 순서와 다를 수 있다.
누적 상한을 넘지 않게 묶음을 줄인다. 아래 첫 번째 보장(나눠 실행해도 같은 순서)은 `k = 1`(기본)에서만 성립하고, 나머지는 `k` 와 무관하다.

같은 입력과 고정된 응답에서 다음이 성립한다.

- `5→10→20`의 질의 순서는 한 번에 `20`을 실행한 순서와 같다.
- 예산이 늘어도 검증한 경로가 사라지지 않는다. 파레토 집합에서 빠지는 비용쌍은 새 검증 결과에 지배된 경우뿐이다.
- 충분한 예산으로 모든 후보를 검증하거나 인증 하한으로 제거하고 미해결 실패가 없으면, 제공된 후보 집합의 정확한 파레토 비용쌍을 얻는다.
- `complete=True`는 마지막 조건을 만족했다는 뜻이다. 예산 소진이나 조회 실패를 최적성 인증으로 취급하지 않는다.

동일 예산의 다른 선택 정책보다 항상 우월하다는 보장은 없다. 현실의 모든 경로를 후보에 넣었거나,
시간표·택시 도착 이후 대기·환승요금까지 정확히 모델링했다는 보장도 아니다.
응답은 한 실행 동안 고정된 것으로 취급한다. 실시간 재조회나 동시 `advance()` 호출은 지원하지 않는다.

## 사용 예

```python
from algo.lazy_pareto import Candidate, Cost, LazyParetoSearch

actual = {"taxi-a": Cost(900, 7000), "taxi-b": Cost(600, 10000)}

async def fetch(query):
    return actual[query]

async def evaluate(candidate, paid):
    return paid[candidate.queries[0]]

search = LazyParetoSearch(
    [Candidate("a", Cost(800, 6500), ("taxi-a",)),
     Candidate("b", Cost(700, 9500), ("taxi-b",))],
    {"transit": Cost(1500, 1500)}, fetch, evaluate, vot=456,
)
first = await search.advance(1)
complete_front = await search.advance(2)
assert search.complete
```
